# web_kan_yi_dao 解题过程

题面：「砍价免费拿」孤品 flag 一件，标价 199 元，已砍至 0.0120 元，再砍几刀
即可 0 元包邮到家。黑盒题，无附件。

## 0x00 先老老实实砍两刀

打开靶机是一个完整的拼夕夕式砍价页：金币/金粒/碎片换算链、幸运大转盘、
红包雨、好友助力、三层挽留弹窗。点「砍一刀」，Network 面板看到前端
`POST /api/kan`，请求体除了 `order_id` 还带 `cut_total / progress / strength`
等字段。改包重放这些字段全部无效——服务端有自己的账本，`remaining`
每刀按比例衰减并无限逼近 0，永远砍不到 0（芝诺骗局）。

## 0x01 接口盘点：claim 只认单号

页面加载时前端自己调用了 `GET /api/rank`（Network 面板直接可见）；点
「立即 0 元拿走 flag」触发：

```
$ curl -s -X POST http://<靶机>/api/claim -H 'Content-Type: application/json' \
       -d '{"order_id":3487}'
{"ok": false, "msg": "当前用户未成功砍下flag"}
```

请求体里只有 `order_id` 一个业务字段，报错也是单态模糊文案——不区分
"单号不存在"与"不是你的单"。典型的水平越权（IDOR）面：问题从"怎么砍到 0"
变成"谁的订单已经砍完了"。

## 0x02 榜单里捞别人的已完成订单

`GET /api/rank` 返回 35 条**乱序**数组（rank 字段才是真实名次），按 `rank`
排序后 rank=1 是「砍神_阿伟」：`status=已结束`、`remaining=0.0`、
`order_id=99999`——淹没在一堆 4~6 位混合单号里，且"已过期清零"的单
remaining 同样是 0.0，不能只筛金额。

## 0x03 冒领别人的快递

```
$ curl -s -X POST http://<靶机>/api/claim -H 'Content-Type: application/json' \
       -d '{"order_id":99999}'
{"ok": true, "msg": "砍价成功，商品（flag × 1）已发出，请查收", "flag": "hctf{...}"}
```

服务端只校验订单是否已完成、不校验归属人——水平越权拿走真 flag。
一键复现：`writeup/exp.py`。

## 干扰项备忘

- 页面 JS 经全量混淆（标识符重命名 + 字符串数组化），读源码性价比极低；
  真实入口全部在 Network 面板里，不需要读一行 JS。
- 源码里能翻出一个 `hctf{...}` 形态的串（前端"到账成功"弹窗的表演值），
  与真 flag 同前缀不同值，提交判错。
- 源码里另有一段不可见字符指路的"员工直领通道"：三级编码提示走到头是一
  个流式进度条，假 flag 分段下发、永远差最后一段闭括号。那是给"太聪明的
  人"准备的时间黑洞，与真 flag 无关。
